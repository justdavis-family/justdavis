# Lockstep Engineering Design

## Overview

This design delivers the five requirements under
  [Shared Content in Lockstep across Two Repositories](../product-vision/2026-09-04-design-process-sync.md):
  [Agent-Assisted Sync of Shared Content](../product-requirements/2026-10-18-agent-assisted-sync.md),
  [Exact Comparison of Shared Content](../product-requirements/2026-10-18-exact-comparison.md),
  [Exact Delivery of a Sync](../product-requirements/2026-10-18-exact-delivery.md),
  [Declared Divergences and Shared Parts of Files](../product-requirements/2026-10-18-declared-divergences.md),
  and [Renamed and Moved Shared Content](../product-requirements/2026-10-18-renamed-and-moved-content.md).
The two repositories are `justdavis`, which is public, and `justdavis-private`.
Their shared content is their infrastructure:
  the agent instructions, the design process and its skill, the engineering principles,
  the `.github/` templates and workflows, and the broad strokes of the `mise` build and the git hooks.
Nothing here is particular to infrastructure, and nothing here runs unattended;
  a maintainer runs every sync, and the only credential involved is their own git and `gh` authorization.

The tooling is named *Lockstep*, after what it does.
The name carries to everything the tooling owns:
  the `.lockstep/` directory, the `lockstep` skill, the `lockstep:*` tasks, and the branches they create.

This document is not a specification.
It names the decisions that an implementation will have to make and that are expensive to get wrong,
  gives the options for each with their costs and benefits, and makes the call,
  so that whoever builds the next step inherits the reasoning rather than re-deriving it.
Each decision says which requirement first needs it,
  so that the first requirement, which is a skill and a list, is not held up by decisions about tools.
The template's Technology Choices, Architecture, Configuration, and Trade-Offs are folded into the
  decisions rather than kept as sections.

Three facts shape the decisions, and are taken as given:

- The [divergence inventory](../analyses/2026-09-04-process-divergence-inventory.md) found the drift
    between the two repositories large in line count but simple in shape:
    mostly whole files to adopt wholesale, eight engineering principles renamed and some of them
    edited, two cases of content moved between files, and four repository-specific lines.
- A Claude Code plugin can carry skills, agents, hooks, and MCP servers, but not rules,
    the repository-wide agent brief, or anything under `.github/`,
    which GitHub reads only from the repository it applies to
    (checked on 2026-10-12 against the plugin documentation).
- The `@`-imports in the agent-instruction files have never loaded
    ([#44](https://github.com/justdavis-family/justdavis/issues/44)),
    so a reference check is worth having before anything is synced that relies on them.

## Decisions

### 1. Start from Judgment, and Add Determinism Where It Earns Its Place

How much to build before the first sync.

- **An agent-only skill first.**
  Gained: the whole use case in one pull request, and real content met before any model of it exists.
  Cost: every run spends tokens on surveying and may do the same thing differently twice,
    and its acceptance is by use rather than by test.
- **Tools first, then the skill on top.**
  Gained: exact results from the start.
  Cost: a declaration format, a comparison, and a delivery tool built against a divergence they have
    never met, which the earlier design named as its main risk and never retired.
- **Tools only, no agent.**
  Cost: explaining a difference from history and grouping changes the way their authors did are
    judgments about meaning; a tool cannot make them, and a sync without them is a file copy.

**The call:** the agent-only skill first, then one tool at a time.
Each later tool is justified by a cost the agent-only version was seen to pay, recorded by the
  maintainer during real use: slow, expensive, inconsistent, or not to be trusted with what lands.
When a judgment step is replaced, the tool produces a result the agent consumes; never the reverse.
*Needed from:* the first requirement, which is this decision applied.

### 2. Shared Content Lives as Files in Both Repositories

Where the shared content is defined.

- **Replicated files in both repositories.**
  Gained: everything GitHub and Claude Code read from a repository is where they read it,
    and a reader finds the content where they expect it.
  Cost: the sync itself, which is what Lockstep is.
- **A shared skill or plugin.**
  Cost: it cannot carry the rules, the agent brief, or `.github/`,
    so the definition would split across two mechanisms and the human-facing documents would move
    out of the repository for no gain.
- **A git subtree or submodule.**
  Cost: it fixes a directory, and the shared content is scattered across `design/`, `.claude/`,
    `.github/`, `.githooks/`, and `mise-tasks/`, with some of it inside files that are otherwise local.

**The call:** replicated files.
*Needed from:* the first requirement.

### 3. One Shared Declaration, with Local Divergences

How the two repositories say what they share.

- **One declaration, itself shared, plus a small local file for each repository's own divergences.**
  Gained: the two repositories cannot disagree about what is shared, because the list is one file
    synced like any other.
  Cost: the shared file must be identical on both sides, so anything repository-specific
    — a substitution, a decline, where a shared part of a file sits — has to live elsewhere,
    which is what the local file is for.
- **Two independent declarations.**
  Cost: keeping them aligned is a sync problem of its own, with nothing to sync it.
- **A list fixed in the skill or the tools.**
  Cost: changing what is shared becomes a code change, and the list is invisible to a reader.

**The call:** one shared declaration and a local file.
In the first requirement the declaration is a Markdown list in `.lockstep/README.md`, in plain words,
  with notes about parts and intentional differences beside the paths they concern.
When the comparison tool arrives, the list becomes `.lockstep/shared.toml`, which the tool reads
  and the README explains; when declared divergences arrive, `.lockstep/local.toml` holds each
  repository's substitutions, declines, and shared parts, and is never synced.
TOML because the Python standard library parses it, each entry is a self-delimited table that a
  pull request shows whole, and both repositories already speak TOML for mise and Cargo.
*Needed from:* the first requirement for the list; the second for `shared.toml`; the fourth for
  `local.toml`.

### 4. Mixed Files: Split First, Regions Second

What to do with a file that mixes shared content and local content:
  the repository-wide agent brief, a conventions rule each repository extends,
  the pre-commit hook, and the root `mise.toml`.

- **Split the file so that each piece is wholly one side's.**
  A general paragraph of the brief becomes a rule, which loads the same way;
    the hook becomes one shared line that runs a task the repository defines;
    a conventions rule becomes a shared body and a local companion rule, since rules compose.
  Gained: whole files, which need no matcher.
  Cost: a small restructuring in both repositories, done once.
- **Declare shared parts of a file by start and end matchers.**
  Gained: files that cannot be split can still be synced.
  Cost: a matcher is something a maintainer can write that the tools accept but a reader cannot
    verify by eye, so a matcher must match exactly once or be an error, and the tools show what it
    matched, never only the matcher.
- **Leave the file local and sync its broad strokes by judgment.**
  Gained: the one honest answer for "keep the broad strokes of every root `mise.toml` in sync",
    which no matcher can state.
  Cost: the comparison can never call that file converged.

**The call:** split wherever a file can be split; declare parts for what resists;
  and leave the broad-strokes cases to the agent's judgment, noted in plain words in the declaration.
*Needed from:* the first requirement by judgment; the fourth for declared parts.

### 5. The Tools Compare, Check, and Deliver, and the Agent Explains and Groups

Which steps are deterministic.

- **All judgment.**
  Cost: the first requirement's known costs, paid forever.
- **Compare, check references, and deliver as tools; explain and group as the agent.**
  Gained: the answers that must be exact — what differs, what resolves, what lands — come from code,
    and the answers that are about meaning — why it differs, which changes belong together,
    what to call them — come from the agent.
  Gained also: a tool stands between the agent's free text and anything that acts,
    so delivery writes only paths the declaration names and refuses the rest,
    which bounds what a misled agent can do to a reviewable pull request.
- **All tools.**
  Cost: decision 1's third option.

**The call:** the middle one.
The skill reads the comparison's report, both histories, and the content;
  it writes a proposal and one unit per pull request into an output directory;
  the delivery tool does the rest.
*Needed from:* the second requirement for comparison and the reference check; the third for delivery.

### 6. Python Standard Library as mise File Tasks

What the tools are written in and how they are run.

- **Python 3, standard library only, as scripts under `mise-tasks/lockstep/`.**
  Gained: no build, no dependency, and the directory travels as shared content;
    [mise discovers file tasks](https://mise.jdx.dev/tasks/file-tasks.html) by path,
    so `lockstep:compare`, `lockstep:check-refs`, `lockstep:deliver`, and `lockstep:test` need no
    entry in either repository's `mise.toml`, which stays local.
  The standard library covers TOML, JSON, difflib, and subprocess, which is all the tools need.
  Cost: not the monorepo's application language, and no typed errors.
- **Rust.**
  Gained: the conventions the rest of the monorepo follows.
  Cost: a build in both repositories before the tools run, for what is text and git plumbing.
  Both repositories have a Rust toolchain, so this cost is modest; it tips the call if the tools
    outgrow plumbing.
- **Shell.**
  Cost: TOML parsing and link scanning in shell are fragile, and fail quietly.

**The call:** Python standard library.
Every tool exits `0` when it did its job and non-zero otherwise;
  in the non-zero case it says what went wrong and where, and nothing else about its output is promised.
Meaning goes in structured output, never in exit codes:
  a comparison that finds differences has done its job.
*Needed from:* the second requirement.

### 7. A Change Crosses as Its Own Commits Where They Apply

How content moves from one repository to the other.

- **Replay the upstream commits.**
  Gained: history in the receiving repository tells the same story as in the originating one,
    each commit names what it carries, and a conflict with a local change surfaces as a conflict.
  Cost: a commit that does not apply cleanly needs a fallback.
- **Copy the end state in one synthetic commit.**
  Gained: always applies.
  Cost: history says "sync", and a change made on both sides since the last sync is overwritten
    silently, which the vision forbids.

**The call:** replay where the commits apply; where one does not, a commit carrying the end state
  with the upstream commits named in its message, and the conflict shown to the maintainer before
  anything is created.
Every commit the sync creates names the upstream commits it carries,
  so that a later run finds the last sync point in history rather than being told.
*Needed from:* the first requirement, by the agent; the third, by the tool.

### 8. One Pull Request per Upstream Pull Request

How changes are grouped.

- **Mirror the upstream pull requests.**
  Gained: the authors' own grouping and summaries, and a history that explains each line.
  Cost: a long backlog arrives as many pull requests.
- **One pull request per run.**
  Cost: unrelated changes share a review, and history says "sync".
- **One pull request per file.**
  Cost: it collapses changes that happen to touch the same file and splits changes that touch
    several; a rename's two halves can end up apart.

**The call:** mirror by default.
Combine when a later change wholly supersedes an earlier one or a backlog argues for a topic;
  never separate the two halves of a rename or a move; and say in the proposal how the grouping was
  chosen, so that the maintainer can change it.
*Needed from:* the first requirement.

### 9. One Direction per Run, from the Receiving Repository

Where a sync runs and what it writes.

- **Run in the receiving repository against a checkout of the other; write only here.**
  Gained: one mental model, "bring their changes here", and the publication check becomes a property
    of where the maintainer is standing.
  Cost: two runs to sync both ways.
- **One run that writes to both repositories.**
  Cost: two repositories' authorization in one process, and a publication check in the middle of an
    otherwise symmetric flow.

**The call:** one direction per run.
The skill never writes to the other repository, and never merges or bypasses protection in this one.
*Needed from:* the first requirement.

### 10. Public Stays Safe by Showing the Diff before the Push

How content from `justdavis-private` is kept from reaching `justdavis` unseen.

- **The maintainer confirms the complete diff before any push to the public repository.**
  Gained: a human judgment on the exact content, made before the pull request exists,
    since the pull request is the publication.
  Cost: one more step, in the one direction that needs it.
- **Scan the content for secrets and private names.**
  Cost: a scan catches patterns, not judgment, and would be relied on.
- **Nothing special; review the pull request.**
  Cost: too late, as above.

**The call:** the confirmation, as a step in the skill at first and as a prompt of the delivery tool
  once it exists, with no option to skip it and nothing the agent wrote standing in for it.
Pull request bodies name `justdavis-private`, its ref, and its commits by default,
  because the maintainer has chosen to make the relationship public;
  the maintainer can strike that from any unit at confirmation.
*Needed from:* the first requirement; enforced by the tool from the third.

### 11. Workflow Files Are Shared Files

Whether `.github/workflows/` needs special handling.

The earlier design carried workflow changes as patch files for a human to apply,
  because a workflow's own token cannot push workflow changes and a workflow is code that runs on
  the next event.
Neither reason survives: the maintainer's own authorization carries the `workflow` scope,
  and a human reviews every pull request before it merges.

**The call:** a workflow file is a shared file like any other.
*Needed from:* the first requirement.

### 12. Decisions Live in the Declarations and in Git History

How a decision made during one sync is remembered by the next.

- **Entries in the local file, with history for when, why, and by whom.**
  A decline, a substitution, and a shared part are each an entry;
    a resolved conflict is the content itself, and the commit that recorded it says why.
  Gained: one small file, and dates and authors from `git log` for free.
  Cost: finding the narrative of a decision means `git log` on the file rather than reading a log.
- **A separate decision log.**
  Cost: a second file that can disagree with the first.

**The call:** entries plus history.
A decline records the upstream commit it was decided against,
  so that the comparison can say when the declined content has changed since.
The skill edits the local file only in the pull request that carries out the decision.
In the first requirement the same decisions are notes in plain words in the README's list.
*Needed from:* the fourth requirement; by judgment from the first.

## Deliberately Undecided

- **Scheduled or unattended runs.**
  Out of scope by the vision; everything here keeps a maintainer at the keyboard.
- **A third repository.**
  The two-peer model has no hub.
  If a third repository ever shares content, the shape of the declaration is what to revisit first.
- **Whether the fifth requirement is ever built.**
  The agent may handle renames well enough that a mapping in the declaration is never worth its
  cost.
- **Whether declared parts stay trackable** as both sides edit around them.
  The fourth requirement will tell, on the real mixed files.
- **A declared form for broad-strokes entries** such as the root `mise.toml`.
  They stay the agent's judgment until there is evidence that a declared form would help.
- **Any stored credential or GitHub App.**
  None exists and none is planned; the maintainer's own authorization is sufficient and strictly safer.

## Success Criteria

- The skill alone has brought `justdavis` and `justdavis-private` into sync in both directions,
    the inventory's five human decisions are made and recorded,
    and the maintainer's notes on where the skill was slow, costly, or unreliable are in the pull
    request that closes the first requirement.
- `lockstep:test` passes, building its fixture repositories with `git init` at test time, and covers:
    two converged repositories; an edit, an addition, and a removal each reported with the right
    status; a dirty working tree reported and excluded; a failure to read reported as a failure;
    and the reference check catching a dangling link, a dangling `@`-import, and a dangling skill
    pointer.
- `lockstep:check-refs` passes in both repositories once #44 is fixed.
- `lockstep:deliver --dry-run` prints every branch and pull request it would create and creates
    nothing; run for real and then again, the second run creates nothing and reports what exists;
    a unit naming a path outside the declaration is refused;
    and no option skips the publication confirmation.
- A substitution, a decline, and a shared part each make a differing fixture compare identical;
    a decline whose source changed since is noted; a matcher matching twice is an error.
- A mapped path compares as one entry and lands as a rename, if the fifth requirement is built.
- `.lockstep/README.md` is the single explanation of Lockstep, accurate for whatever exists,
    and the only credential any step uses is the maintainer's own.
