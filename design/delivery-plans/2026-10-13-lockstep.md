# Lockstep Delivery Plan

## Overview

This plan sequences delivery of the six requirements under
  [One Development Process across Many Repositories](../product-vision/2026-09-04-design-process-sync.md)
  — [Propose a Process Sync](../product-requirements/2026-09-06-process-sync-proposal.md),
  [Apply a Process Sync Proposal](../product-requirements/2026-09-06-process-sync-apply.md),
  [Remember Sync Decisions](../product-requirements/2026-09-08-sync-decisions.md),
  [Unattended Sync Proposals](../product-requirements/2026-10-04-unattended-sync-proposals.md),
  [Publish Approved Outbound Changes](../product-requirements/2026-10-04-publish-outbound-changes.md),
  and [Enroll a New Repository](../product-requirements/2026-10-12-enrolling-a-repository.md) —
  into seven milestones, following the
  [Lockstep Engineering Design](../engineering-designs/2026-10-13-lockstep.md).
Six of the seven land in this repository, the hub.
One lands in the first follower, a private repository that this plan describes but never names.

The main delivery risk is **building automation on a model that has never met real content**.
Three things in the design are untested until they are used:
  whether regions and divergences keep a mixed file trackable,
  whether the grouping heuristics produce a history a reviewer would want,
  and whether `claude-code-action` accepts a read-only token in the way the containment argument
  needs.
The ordering answers that by putting every tool through real use by hand, on the real divergence the
  [inventory](../analyses/2026-09-04-process-divergence-inventory.md) measured,
  before any workflow exists:
  the comparison and enrollment first, then the hub's own content made adoptable,
  then the skill, then delivery, then the first follower converged with those tools,
  and only then publication and the unattended run.
Enrollment is built first because every later milestone uses it to put the tooling in front of
  real content, and it is proven last, once everything it copies exists.
The hub's content changes come before the follower's convergence on purpose,
  so that the follower's first sync is mostly adoption rather than conflict.

Four things later milestones depend on are not in hand:

- **The `@`-import fix**, tracked in
    [#44](https://github.com/justdavis-family/justdavis/issues/44),
    which the reference check in the first milestone will fail without.
  It is its own small pull request, not a milestone here.
- **Two repository settings no pull request can change**, both made by hand by an organization
    admin: the hub's admin bypass on `main` narrowed from "always" to "for pull requests only",
    before the first milestone; and "Allow GitHub Actions to create and approve pull requests"
    turned on in the follower, before the unattended milestone.
- **The action's behavior with a read-only token**, which the design flags as unverified and the
    unattended milestone confirms first, with the weaker fallback already written down.
- **Five human decisions** the inventory's recommendation lists, which this plan records below
    under the milestones that carry them out, so that they are made once and in writing.

## Delivery Conventions

- **Each milestone ships as its own merged pull request.**
  The follower's milestone ships as a pull request there; its tracking issue here closes when
    its maintainer reports it merged, and names nothing about where.
- **The README is built incrementally.**
  Every milestone leaves `.lockstep/README.md` accurate for the tools that exist at that point,
    and it says plainly which parts of Lockstep do not exist yet.
- **Enrollment grows with the tooling.**
  Every milestone that adds a piece a follower must hold extends what `lockstep:enroll` copies,
    so that the tool is never behind the process it enrolls a repository into.
- **Every tool arrives with its tests**, built on fixture repositories per the design,
    and `lockstep:test` is wired into the root `ci` task in the milestone that creates it.
- **Nothing a milestone creates in the hub names a private repository**, in content, commit
    message, or pull-request description.
- **A milestone pull request in the hub attaches no output produced in a private repository.**
  Evidence from real content stays in that repository; evidence in the hub comes from fixtures.
- **Settings changes are recorded in the pull request** that first depends on them,
    since no document in the repository can carry them.
- **Neither repository holds a credential for the other, at any milestone.**
  The only secrets in a follower are those the review workflow already needs;
    a milestone that would add one is a change to the design first.

## Milestones

### M1 — The Catalog, the Comparison, the Reference Check, and Enrollment

**Deliverable:** a maintainer can run one command in the hub to give any repository a manifest
  adopting the hub's catalog, then one command there to read, per adopted entry, whether it is
  identical, differs, or is missing, with declared divergences and regions honored;
  and a maintainer of the hub can run one command and learn of every dangling link, import,
  and skill pointer in the process content.

**Deferred:** the skill and any explanation of *why* an entry differs; delivery; the workflow.
Nothing in this milestone changes any process content.

**In scope:**

- `.lockstep/` in the hub, with the catalog listing every file the inventory found inside the
    process scope and the README's first version: what the directory is, what exists so far,
    the by-hand steps for the tools that exist, and which files a reader might assume are shared
    but are each repository's own or adopted only in part.
  A line in `CONTRIBUTING.md` points at it.
- `mise-tasks/lockstep/compare` and `mise-tasks/lockstep/check-refs`, with the shared
    package beside them, implementing the comparison and the reference check as the design
    specifies: path or URL counterparts, regions, replace and patch divergences,
    declines with `as_of`, the seven statuses, the report's outcome and exit, and the unattended
    refusal.
- `mise-tasks/lockstep/enroll`, copying the task directory and the README into a working tree
    and writing a manifest that adopts every catalog suggestion, with suggested regions and
    replacements copied in; later milestones extend what it copies.
- `mise-tasks/lockstep/test` and the fixture tests the design's success criteria list for these
    tools, wired into the root `ci` task.
- Enrollment run against the first follower's working tree, and the comparison run there,
    so that the comparison meets the real divergence in this milestone.
  Whether that manifest is committed in the follower now or held until its convergence milestone
    is the maintainer's call at the time.

**Acceptance criteria:**

- [ ] Every test the design's success criteria name for the comparison, the reference check,
        and enrollment passes, and `lockstep:test` runs in `ci`.
- [ ] `lockstep:check-refs` passes in the hub, after the `@`-import fix has merged.
- [ ] Both commands run without an agent and need no credential against the public hub
        (from [Propose a Process Sync](../product-requirements/2026-09-06-process-sync-proposal.md)).
- [ ] A failure to compare an entry is reported as an error and never as identical
        (from [Propose a Process Sync](../product-requirements/2026-09-06-process-sync-proposal.md)).
- [ ] Run with `LOCKSTEP_UNATTENDED` set, the comparison refuses any counterpart other than the
        manifest's hub and refuses to clone, exiting non-zero.
- [ ] Enrollment writes only to the new repository's working tree, so that nothing in the hub
        changes (from [Enroll a New Repository](../product-requirements/2026-10-12-enrolling-a-repository.md)).
- [ ] The comparison, run in the first follower after enrollment, reports the divergence the
        inventory measured, with every status accounted for; the pull request describes that in
        prose and attaches no output from it.
- [ ] The hub's admin bypass on `main` is "for pull requests only", recorded in the pull request.
- [ ] The README documents the tools that exist, says the rest of Lockstep does not exist yet,
        and names the files a reader might assume are shared as each repository's own or adopted in
        part (from [Propose a Process Sync](../product-requirements/2026-09-06-process-sync-proposal.md)).

### M2 — Make the Hub's Content Adoptable

**Deliverable:** the hub's process content can be adopted by a follower without a divergence except
  by choice: the repository-specific lines are generalized, the mixed files are split so that each
  part is wholly one side's, and the improvements the inventory found only in the follower are in
  the hub.

**Deferred:** anything in the follower; the skill.
This milestone is done by hand, with the comparison from M1 as its check.

**In scope:**

- The two textual fixes the inventory found: `supersede` in `design/README.md`
    and "delivery plans" in the review workflow's prompt.
- The centralized-configuration engineering principle, adopted into the hub.
- A dependency-audit workflow for the hub's Rust projects, equivalent to the follower's.
- The four repository-specific lines generalized: a placeholder example URL in the requirements
    template, a relative link in the pull-request template, and the label-automation issue link in
    the PR workflow rule kept as the catalog's one suggested replacement.
- The mixed files split where the design says a split is preferred:
    the evergreen-content guidance moved from the repository-wide brief into a rule;
    the pre-commit hook reduced to one shared line that runs a task the repository defines.
- The catalog updated for every file this milestone adds, splits, or generalizes.

**Human decisions this milestone records** (from the inventory's recommendation):

- The two textual fixes are taken.
- The centralized-configuration principle is adopted in the hub.
  It is project-agnostic, and the follower's own earlier analysis recommended it.
- A dependency-audit workflow is adopted in the hub, since the hub now has Rust projects.
- The four repository-specific lines are generalized rather than declared divergences,
    except the issue link, which stays as the catalog's suggested replacement.

**Acceptance criteria:**

- [ ] Both textual fixes are in; the principle and the audit workflow exist in the hub and the
        catalog lists them.
- [ ] No process file in the hub names a hub-specific issue, URL, or path except the one suggested
        replacement.
- [ ] The repository-wide brief holds nothing the catalog offers; the rule that took its general
        guidance loads the same way, which the pull request shows.
- [ ] The content this milestone brings from the follower was confirmed safe to publish by a
        human before the pull request was opened
        (from [Apply a Process Sync Proposal](../product-requirements/2026-09-06-process-sync-apply.md)).
- [ ] The pull request's commits and description name no private repository.

### M3 — The Skill and the Proposal

**Deliverable:** a maintainer in a repository with a manifest can invoke the `lockstep` skill
  and receive a proposal that explains every difference from history, groups the differences into
  units with rationale, raises every decision only a human can make with a recommendation,
  and writes one unit directory per proposed pull request, changing nothing in either repository.

**Deferred:** delivery; any unattended use.

**In scope:**

- `.claude/skills/lockstep/`: `SKILL.md`, `proposal-format.md`, and `grouping.md` with the
    design's starting heuristics and its procedure for finding each entry's base in the hub's
    history.
- The output directory layout, the unit id, and the patch authoring the design describes,
    including divergences put back and regions written in place.
- Enrollment extended to copy the skill.
- The README's section on reading a proposal and answering its decisions.
- A fixture with a backlog of a dozen overlapping hub pull requests and one follower file edited
    by hand, so that finding the base and grouping are exercised on the shape of the real backlog.
- A proposal produced on the backlog fixture, attached to the pull request as the worked example.
- A first real proposal, produced in the first follower against the hub as converged by M2 and
    read by the maintainer there; the pull request says that it was, and attaches nothing from it.

**Acceptance criteria:**

- [ ] For each difference, the proposal names the commits and pull requests that produced it and
        classifies it as an edit, addition, removal, rename, rename plus edit, or move
        (from [Propose a Process Sync](../product-requirements/2026-09-06-process-sync-proposal.md)).
- [ ] No unit separates the two halves of a rename or a move, and the proposal states how it
        grouped and why
        (from [Propose a Process Sync](../product-requirements/2026-09-06-process-sync-proposal.md)).
- [ ] On the backlog fixture, every entry's base is found by provenance, content match, or nearest
        version as the design specifies, and the hand-edited file is reported as the follower's
        own change rather than folded into an inbound unit.
- [ ] Every decision the proposal cannot make is listed with a recommendation and the manifest
        entry that would record it (from [Propose a Process Sync](../product-requirements/2026-09-06-process-sync-proposal.md)).
- [ ] Against two converged fixture repositories, the proposal is empty (from [Propose a Process Sync](../product-requirements/2026-09-06-process-sync-proposal.md)).
- [ ] A unit whose content originates in a private repository and is bound for a public one,
        in either direction, is marked as needing clearance (from [Propose a Process Sync](../product-requirements/2026-09-06-process-sync-proposal.md)).
- [ ] Where an inbound rule is one the repository's local content does not follow, the proposal
        names the affected content and the unit leaves it unchanged (from [Apply a Process Sync Proposal](../product-requirements/2026-09-06-process-sync-apply.md)).
- [ ] The skill reads commit messages and content only, never pull-request bodies or comments,
        and the skill's instructions say so.
- [ ] The pull request attaches no output produced in a private repository, and names none;
        the attached example comes from the fixture.

### M4 — Attended Delivery

**Deliverable:** a maintainer who has read a proposal can turn it into branches and pull requests
  in their repository, questions for held units, and approval requests for outbound units, with
  one command, after seeing exactly what it will create.

**Deferred:** publication to the hub; the workflow.

**In scope:**

- `mise-tasks/lockstep/deliver` as the design specifies: the dry run, the branch pattern, the
    watermark, idempotent updates and closures, `--onto` for landing units on an existing branch,
    `pending/` carriers for workflow files,
    `Lockstep decision` issues, `Lockstep out` issues with the content hash and the verdict sentences,
    the typed confirmation that clears a unit needing clearance,
    and the trust boundary in the design's "What the Deliver Tool Trusts".
- Its fixture tests, added to `lockstep:test`.
- The README's by-hand sequence completed through delivery.

**Acceptance criteria:**

- [ ] `lockstep:deliver --dry-run` prints everything it would create and creates nothing;
        run for real and then again, the second run creates nothing and reports what exists.
- [ ] It refuses a unit naming a path outside those the design's trust rule allows, and carries a
        workflow file as a patch under `pending/` rather than writing it.
- [ ] Each applied unit becomes one branch and one pull request following the repository's
        conventions, with provenance in the description
        (from [Apply a Process Sync Proposal](../product-requirements/2026-09-06-process-sync-apply.md)).
- [ ] Local content is byte-for-byte unchanged apart from the unit's consistency edits and a carrier
        (from [Apply a Process Sync Proposal](../product-requirements/2026-09-06-process-sync-apply.md)).
- [ ] A unit with an open decision yields one `Lockstep decision` issue and no pull request;
        recording the decision in the manifest and running again yields the pull request and closes
        the issue.
- [ ] If the base ref has moved since the proposal, or a patch no longer applies, delivery stops
        before creating anything and says what changed (from [Apply a Process Sync Proposal](../product-requirements/2026-09-06-process-sync-apply.md)).
- [ ] For an inbound unit that needs clearance, delivery shows the complete diff and creates nothing until
        the maintainer types the confirmation that clears it (from [Apply a Process Sync Proposal](../product-requirements/2026-09-06-process-sync-apply.md)).
- [ ] With `--onto`, inbound units land as commits on the named branch and no pull request is
        opened, so that enrollment can be one pull request
        (from [Enroll a New Repository](../product-requirements/2026-10-12-enrolling-a-repository.md)).
- [ ] A `Lockstep out` request records an approval, a refusal, or a withdrawal as its verdict;
        a refused request is closed by the next run with the manifest entry that would record it
        (from [Unattended Sync Proposals](../product-requirements/2026-10-04-unattended-sync-proposals.md)
        and [Publish Approved Outbound Changes](../product-requirements/2026-10-04-publish-outbound-changes.md)).
- [ ] A decision is recorded in the same pull request that carries it out
        (from [Remember Sync Decisions](../product-requirements/2026-09-08-sync-decisions.md)).

### M5 — Converge the First Follower

**Deliverable:** the first follower holds a manifest, and a comparison between it and the hub reports
  every adopted entry identical; the five-month backlog is closed, with each decision recorded.
This milestone lands in the follower.

**Deferred:** nothing automated; publication of anything outbound, which M2 already carried by hand.

**In scope:**

- The Lockstep tooling put in place by `lockstep:enroll`, and the manifest it wrote reviewed and
    edited.
- The proposal from M3 regenerated against the current hub and delivered with M4's tool,
    in as many pull requests as the grouping produces.
- The follower's own mixed files handled as the design prefers:
    its conventions-rule additions moved into a local companion rule,
    and anything that resists a split adopted by region.
- Every decision recorded in the manifest, with reasons.

**Human decisions this milestone records** (the first from the inventory's recommendation,
  the rest from the design's handling of mixed files and side-only content):

- The eight shared engineering principles take the hub's names and dates;
    the follower renames its copies and updates its local references in the same pull request.
- The follower's local additions to the conventions rule stay local, as a companion rule.
- Content present only in the follower that the hub did not adopt in M2 is declined in the
    follower's manifest with a reason, or adopted by the hub through a later outbound unit.

**Acceptance criteria:**

- [ ] `lockstep:compare` in the follower reports every adopted entry identical and every
        catalog suggestion adopted or declined.
- [ ] `lockstep:check-refs` passes in the follower.
- [ ] Each pull request's description explains the lines it touched and names its provenance
        (from [Apply a Process Sync Proposal](../product-requirements/2026-09-06-process-sync-apply.md)).
- [ ] Every synced commit names the hub commit it carries, so that every later proposal finds its
        base by provenance rather than by content search.
- [ ] Every mixed file is either split or adopted by region, and the pull requests record which,
        so that the design's open question about regions has an answer.
- [ ] The tracking issue for this milestone here names no private repository.

### M6 — Publish Approved Outbound Changes

**Deliverable:** a change approved on a follower's approval request reaches the hub as a pull
  request through one command run by a maintainer, who sees the exact diff first and whose own
  authorization is the only credential involved.

**Deferred:** the workflow.

**In scope:**

- `mise-tasks/lockstep/publish` as the design specifies: the approval check, the hash and
    branch checks, the shown diff and `yes`, the hub branch and pull request, and the comment that
    closes the loop.
- Its tests, added to `lockstep:test`, against fixture repositories and a fixture approval.
- The README's sections on the outbound path: approving, refusing, and withdrawing;
    publishing by hand; what the hub's reviewers see;
    and what a maintainer of a private repository checks before approving.
- One real outbound change published from the first follower, if any remains after M2 and M5;
    otherwise a scratch change, published and then closed, with that said in the pull request.

**Acceptance criteria:**

- [ ] Against an approval whose hash no longer matches, or a request refused or withdrawn,
        publication refuses; against a valid one it shows the diff and, after `yes`,
        opens one pull request in the hub
        (from [Publish Approved Outbound Changes](../product-requirements/2026-10-04-publish-outbound-changes.md)).
- [ ] The hub pull request's commits and description name no private repository, ref, commit,
        or author unless the approver chose to include them
        (from [Publish Approved Outbound Changes](../product-requirements/2026-10-04-publish-outbound-changes.md)).
- [ ] Run again for the same approval, publication creates nothing (from [Publish Approved Outbound Changes](../product-requirements/2026-10-04-publish-outbound-changes.md)).
- [ ] Neither repository holds any credential for the other (from [Publish Approved Outbound Changes](../product-requirements/2026-10-04-publish-outbound-changes.md)).

### M7 — The Unattended Run, and Enrollment Proven End to End

**Deliverable:** a follower learns of every process change merged in the hub within a day, as a
  parked pull request or a question, without anyone running anything; the hub's copy of
  the workflow runs and does nothing; and a new repository can be brought onto the whole process,
  unattended sync included, with one command in the hub and one sync there.

**Deferred:** nothing; this closes the plan.

**In scope:**

- `.github/workflows/lockstep.yml` as the design specifies: the four jobs, the plain step that
    clones and compares before the agent, the agent's allowance under the no-exfiltration rule,
    the egress block behind it, the token scan before upload, the one-day artifact,
    and the failure issue.
- The egress block set up in two passes: one run in an audit mode that logs every host the agent's
    job reaches, then the block of everything but those the agent needs,
    with the list and the reason for each recorded in the workflow.
- The read-only-token confirmation the design flags, done first;
    if the action does not accept it, the documented fallback and its weaker claim recorded in the
    design and the pull request.
- The workflow applied in the follower by hand, as the design's patch rule requires,
    and the follower's "create and approve pull requests" setting turned on, recorded in the
    pull request.
- Enrollment extended to copy the workflow file, and the README's enrollment section completed:
    the prerequisites and settings, the enrolling sync, declaring divergences,
    and confirming the result.
- Enrollment proven end to end on a scratch repository, then torn down.

**Acceptance criteria:**

- [ ] A pull request created by the unattended run in the follower shows its workflow runs parked
        until a maintainer approves them
        (from [Unattended Sync Proposals](../product-requirements/2026-10-04-unattended-sync-proposals.md)).
- [ ] Against a converged hub a run creates nothing; against a hub with one merged process change
        it opens one pull request within a day (from [Unattended Sync Proposals](../product-requirements/2026-10-04-unattended-sync-proposals.md)).
- [ ] The workflow's first run in the first follower, against the state the by-hand convergence
        left, creates nothing; the pull request says so and attaches nothing from it.
- [ ] The propose job fails before uploading when a file under `out/` contains the OAuth token's
        value, demonstrated on a fixture.
- [ ] The agent's allowance meets the design's no-exfiltration rule, naming no tool that accepts
        a network destination, checked in review.
- [ ] With the egress block in place, a command in the agent's job that tries to reach any host
        other than Anthropic's API fails, demonstrated on a fixture; the hosts allowed were found
        by an audit run and are listed in the workflow.
- [ ] The hub's copy of the workflow runs and creates nothing, and the hub's content and history
        contain no follower's name.
- [ ] A failed run, including one whose comparison's outcome is `error`, opens or updates the
        failure issue
        (from [Unattended Sync Proposals](../product-requirements/2026-10-04-unattended-sync-proposals.md)).
- [ ] Enrolling a scratch repository and running one sync yields one pull request there, after which
        the comparison reports every adopted entry identical and the unattended run is on
        (from [Enroll a New Repository](../product-requirements/2026-10-12-enrolling-a-repository.md)).
- [ ] Nothing in the hub changes and the hub records nothing about the new repository
        (from [Enroll a New Repository](../product-requirements/2026-10-12-enrolling-a-repository.md)).
- [ ] The documentation covers enrollment end to end, including the settings no pull request can
        turn on.

## Explicitly Deferred (Out of Scope for This Plan)

- **Judgment-based sync entries.**
  An instruction such as "the children and tasks differ, but keep the broad strokes of every root
    `mise.toml` in sync so that improvements carry across" cannot be declared as a matcher,
    and the design keeps the comparison deterministic so that "converged" means something and the
    unattended run can be trusted.
  It is likely to be wanted.
  The probable shape is a third kind of entry declared as a sentence, reported by the comparison
    as needing judgment rather than as identical or differing, and read by the skill in attended
    runs only.
  Deferred to see how far regions and divergences get first.
- **An App-based outbound path.**
  The analysis names it as the upgrade if outbound volume ever justifies it; nothing today does.
- **A second follower.**
  Enrollment is proven on a scratch repository; a real second follower is a later plan's concern,
    and the hub learns nothing when one arrives.
- **A "required tasks present" check for root `mise.toml` files.**
  The design keeps that file each repository's own;
    a check is worth adding only if drift bites.
- **Hardening of the hub's mention-responder workflow**, which the design notes reads comments from
    anyone.
  It is outside this design and tracked in
    [#54](https://github.com/justdavis-family/justdavis/issues/54).
- **The analyses template** ([#42](https://github.com/justdavis-family/justdavis/issues/42)),
    **the test-coverage criteria altitude**
    ([#43](https://github.com/justdavis-family/justdavis/issues/43)),
    and **whether a requirement's checkboxes are ever ticked**
    ([#45](https://github.com/justdavis-family/justdavis/issues/45)),
    filed along the way and unrelated to delivery.
